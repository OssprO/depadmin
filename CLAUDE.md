# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Mobile-first web app to manage maintenance fees for a 10-unit building ("Edificio Correspondencia 63"). It replaces a monthly PDF report shared over WhatsApp.

- **`docs/SPEC.md`** is the source of truth for business rules and roles.
- **`docs/PLAN.md`** holds the agreed stack, the hexagonal architecture, the data-model changes to the spec, the phased plan and the open questions with their default answers. Read both before implementing domain logic. Decisions are recorded as ADRs in `docs/adr/`.

**Language:** code (identifiers, tables) is in English, and the UI is in Spanish. Map business terms through the glossary in PLAN.md section 3 (depto → `Unit`, turno → `Shift`, egreso → `Expense`, bitácora → `AuditLog`, and so on).

**Working mode:** one phase per PR. Explain the reasoning behind a design before implementing, include tests, and wait for the user's approval before starting the next phase.

**Current state:** phases 0–4, 6–11b and 12 are merged into `develop`; only phase 5 (deployment, postponed) remains of the first plan. Stage 2 (`docs/PLAN-ETAPA-2.md`) continues the numbering from phase 12. Phase 12 put the building's history inside the books (ADR-0023): the books start in May 2022 from the transcription of the paper sheets, and the platform goes live at the cut-over, August 2026; its data lives outside the repo in `../../Documents/importacion/`, because it names the neighbors. Phase 13a (`feat/fase-13a-captura-y-apariencia`, ADR-0024) reworks capture and looks: income and expense types apart, a payment's observations printed for its depto, «Atrás», the OS theme and green/red accents; 13b adds tablet and desktop layouts.

## Layout & tooling

pnpm 11 workspace: `backend/` (`@depadmin/backend`, NestJS 12 in ESM), `frontend/` (`@depadmin/frontend`, React 19 + Vite 8 + Tailwind v4 + shadcn/ui) and `packages/shared/` (`@depadmin/shared`, Zod contracts). TypeScript 6.0 everywhere, with strict options in `tsconfig.base.json`. Don't add Nx or Turborepo.

### Gotchas

- **Backend imports:** relative imports need a `.js` extension (ESM). Don't use `import type` for classes injected through constructors, because Nest DI relies on `emitDecoratorMetadata`. For the same reason the backend has no `verbatimModuleSyntax` or `consistent-type-imports`.
- **Changing `packages/shared`:** rebuild it (`pnpm --filter @depadmin/shared build`, or keep `pnpm dev` running). Consumers import its `dist/`.
- **Adding shadcn components:** run `pnpm exec shadcn add <component>` from `frontend/`. The `@/*` alias must stay in `frontend/tsconfig.json`; without it, shadcn writes to a literal `frontend/@/` folder with a broken `cn` import.
- **Dependencies with install scripts:** pnpm 11 fails the install until the package is listed under `allowBuilds` in `pnpm-workspace.yaml`.
- **Shared HTTP setup:** `configureApp()` in `backend/src/platform/http/` holds the global prefix and other HTTP setup, and e2e tests use it too. Put new global HTTP setup there, not in `main.ts`.
- **Domain tests:** assert errors by code with `toThrow(withCode('MONTH_CLOSED'))` from `backend/test/support/domain-error.ts`. Shared test builders for a module go in `domain/testing.ts`, which is excluded from the build and from coverage. `*.spec.ts` files are exempt from the boundary rule so they can import vitest.
- **Domain dates:** use `LocalDate` and `YearMonth` from the shared kernel, never `Date`. Calendar math in `shared-kernel/calendar.ts` doesn't depend on the host time zone, and "today" comes from the `Clock` port.
- **Prisma 7:** the config is in `backend/prisma.config.ts` (it loads `.env` itself). The client is generated into `backend/src/platform/prisma/generated/`, which is gitignored and excluded from lint, so run `pnpm db:generate` after editing `schema.prisma`. CHECKs, exclusion constraints and the audit triggers live as hand-written SQL in the migration, and Prisma's diff ignores them, so add new ones by hand (`prisma migrate dev --create-only`, then edit). Prisma refuses `migrate reset` when an AI agent runs it, so ask the user to run it.
- **Repositories:** a domain declares the port and its DI token (e.g. `UNIT_REPOSITORY` in `units/domain/unit-repository.ts`). The adapter in `infrastructure/` uses `PrismaDatabase.db`, which joins the current `UnitOfWork.run()` transaction through AsyncLocalStorage. Conversions such as `toDbMonth` live in `platform/prisma/db-values.ts`. Integration specs call `useTestDatabase()` from `backend/test/support/database.ts`, which truncates everything except `audit_log` and reseeds the ten units before each test.
- **Authentication is on by default:** a global guard requires a Bearer access token on every route. Mark public routes with `@Public()` and read the caller with `@CurrentActor()` (both in `platform/http/auth.ts`). Authorization (superadmin only, write windows) belongs in the use case through domain policies, never in a guard.
- **HTTP errors:** throw `DomainError` subclasses; `ProblemDetailsFilter` turns them into RFC 9457 responses with the error `code` (validation 422, conflict 409, unauthenticated 401, forbidden 403, not found 404). Validate request parts with `new ZodValidationPipe(schema)` using the shared contracts (400 `VALIDATION_FAILED`). Add a Spanish message for every new code in `frontend/src/lib/error-messages.ts`.
- **Auditing a write use case:** inject `AUDIT_TRAIL` (a shared-kernel port; the global `AuditModule` provides it). Declare the entity's `AuditSubject` once in the module's `application/` (see `identity/application/user-audit.ts`; wrap secrets in `Redacted`). Call `trackChanges(subject, entity)` before mutating, then `audit.record(actor, tracked.change('ACTION_CODE'))` inside `unitOfWork.run()` (`creationOf` for new entities). Recording outside a unit of work throws, in the Prisma adapter and in the spec fakes (`FakeUnitOfWork`, `RecordingAuditTrail` in `backend/test/support/audit-trail.ts`). Add Spanish labels for new actions, entities and fields in `frontend/src/features/audit/labels.ts`. `audit_log` is never truncated, so integration specs that read it filter by their own entity or id.
- **Cross-module calls:** a module reaches another only through its `application/` exports, and its Nest module imports the other's (e.g. `ShiftsModule` imports `UnitsModule` and `BillingModule`). The graph has no cycles: `history` → `reports`, `cashbook`, `settings`, `units`; `reports` → `cashbook` → `shifts` → `billing` → `units`, `settings`. Current exports: `ListUnits`/`UnitStatuses` and `RenameUnitOwner` (units), `GetReportingStart`, `StartBooksWithHistory` and `GetMonthHistory` (reports), `GetRates` and `RecordEarlierRates` (settings), the penalty and fee use cases and `GetAccountStatements` (billing), `LoadShiftCalendar` (shifts; its `ShiftCalendar` is the `ShiftResponsibility` that `WriteAccessPolicy` needs), `ReadCashbook` and `ImportMovements` (cashbook). A module also publishes the types others read with `export type { … } from '../domain/index.js'` in its `application/index.ts`. When a lower module needs to ask a higher one (whether a month is open), the question is a shared-kernel port provided globally: `MONTH_LEDGER`, answered by `reports` (the same pattern as `AUDIT_TRAIL`); `PAPER_RECORD`, answered by `history`, is the same for the reports. `WriteAccessPolicy` lives in the shared kernel. Shared in-memory fakes live in each module's `application/testing.ts` (e.g. `buildingWith`, `initialRates`); a module's `testing.ts` may not import another module's domain.
- **Dates in specs:** use `FixedClock` from `backend/test/support/clock.ts` (`FixedClock.on('2026-10-02')`). API specs pin it with `useTestApp({ clock })` and create users with `givenAccounts`/`tokenFor` (`test/support/accounts.ts`). `useTestDatabase()` empties `rate_change`, so seed the rates in specs that charge anything.
- **Writing the books:** rows go through `AddMovement`/`ReviseMovement`/`RemoveMovement` (cashbook), plus `RecordCleaningVisits` for several visits at once, which share `CashbookAccess` (write window plus month open, and `assertConsistent` for rules that span months). Reading a month is `GetMonthlyReport` (reports), which recomputes balances, payment coverage and accounts on every read; `GetMonthHistory` lists every month. `CloseMonth`/`ReopenMonth` change a month's status, with the rules in `ReportLedger.closingBlocker`; views ask `mayClose`/`mayReopen` so they offer only what the use case accepts. Balances of open months need `liveTotalsOf`. Book specs that need everything wired use `booksFixture(today)` from `reports/application/testing.ts`; lower modules use `FakeMonthLedger` (`test/support/month-ledger.ts`).
- **Initial load:** a depto's debts from before its account starts are ordinary `Charge`s dated before the cut-over month (the start month without a history); its adelanto is an `OpeningCredit` that `GetAccountStatements` turns into a payment dated the day before the cut-over (`openingPayment`), so allocation needs no special case. `SetOpeningBalance` (reports) checks the start and the lock (the cut-over month closed), then calls billing's `ReplaceOpeningBalance`.
- **The building's history** (ADR-0023): the books may start before the platform. `ReportingStart` has `month` (first month), `openingBalance` and `cutover` (first live month; equal to `month` without a history), and `ReportLedger.isHistory(month)` tells the months between. Those are ordinary months (rows in `cash_movement`, opened, closed and reopened as usual) with four differences: opening one charges no fees and is not audited (`MonthOpening`); account statements count payments from the cut-over only (`GetAccounts`), and the opening load is dated before the cut-over; the rotation begins at its anchor (`ShiftRotation.firstMonth`), so before it nobody is responsible (`beforeRotation`) and only the superadmin writes; and writing their rows is not audited (`CashbookAccess.isHistory`, from `MonthLedger.cutover()`). Closing and reopening them is audited: closing a month of the history is checking it. Module `history` holds the import (`ImportHistory`: `StartBooksWithHistory`, `RecordEarlierRates`, `ImportMovements`, then the sheets, all in one unit of work, only while the books have not started) and the paper sheets (`paper_sheet`: the paper's figures, alerts, «Responsable», a line per depto as written, and the ids of the rows the sheet lists). The monthly PDF asks the `PAPER_RECORD` port (provided globally by `history`) for a month of the history and prints one document per sheet. A month is compared with its paper by `ownGap` and `carriedGap`, shown in the book's «Hoja de papel» card. The import file is `historyFileSchema` (shared, version 2); JSON bodies accept up to 1 MB for it (`configureApp`).
- **The PDF report:** `RenderMonthlyReport` builds a plain `ReportDocument` and hands it to the `REPORT_RENDERER` port; the layout is `reports/infrastructure/pdf/monthly-report-pdf.tsx` (@react-pdf/renderer, JSX compiled by the backend's tsconfig). Accounts in a report are as of the month's end (`GetAccounts.all(month)`), so a closed month's PDF never changes. It uses the standard PDF fonts, which only draw WinAnsi characters: write `-`, never the minus sign `−`. The observations text (`infrastructure/pdf/format.ts`) copies the building's style; its specs use cases from the real sheets.
- **Scheduled jobs:** wrap the task in `runJob` (`platform/jobs/run-job.ts`). They live in `<module>/jobs/` (a driving adapter like `http/`, enforced by the boundary rule) and use `@Cron` from `@nestjs/schedule` with `BUILDING_TIME_ZONE`. A job calls a use case and logs failures instead of throwing. Changes made with nobody behind them are recorded under `SYSTEM_ACTOR`: `AuditTrail.record` takes a `ChangeAuthor` (`Actor | SystemActor`), while user use cases keep taking `Actor`. `JOBS_ENABLED=false` turns jobs off; the test setups set it.
- **Racing writes:** the domain checks first; a database constraint catches two requests that pass at once. Wrap such writes in `translateViolations` (`platform/prisma/db-errors.ts`) so the constraint's name maps to the same `ConflictError` the domain throws. Anything that writes a month's rows calls `MonthLedger.holdOpen(month)` inside its unit of work before checking the month is open; `CloseMonth` locks the row exclusively (ADR-0021). Test races in `test/concurrency.int-spec.ts`.
- **Errors inside a transaction:** a use case that must persist something and still fail (e.g. revoking a session on refresh-token reuse) returns an outcome from `unitOfWork.run()` and throws after it; throwing inside rolls the write back.
- **Time:** `Clock` (token `CLOCK`, provided globally by `platform/clock`) gives `today()` in America/Mexico_City and `now()` as an `Instant`. Use `Instant` for expiries, never `Date`, in domain and application code.
- **API integration specs:** `useTestApp()` from `backend/test/support/app.ts` boots the real `AppModule` on the Testcontainers database (pair it with `useTestDatabase()`); it resets the login rate limiter before each test.
- **Env vars:** new environment variables must be added to the Zod schema in `backend/src/platform/config/env.ts` and to `backend/.env.example`.

## Architecture rules

- **Backend:** hexagonal modules under `backend/src/modules/<module>/{domain,application,infrastructure,http,jobs}`, plus `<module>.module.ts`, `shared-kernel/` and `platform/`. `eslint.config.js` (`hexagonalPolicies`) enforces this layout. `domain/` and `shared-kernel/` cannot import any package or Node API.
  - `domain/` is plain TypeScript. It never imports Nest, Prisma or another module.
  - Modules talk to each other only through use cases or queries, never through each other's repositories.
- Each use case is one class. A write use case runs inside a `UnitOfWork` transaction that also writes its `AuditLog` entries.
- Domain errors are mapped to RFC 9457 Problem Details by a global filter.
- **Money** is integer centavos wrapped in a `Money` value object. Never use floats.
- The **backend is the authority** for money and shift calculations. The frontend only displays results and validates forms with the shared Zod schemas.

## Domain rules that drive architecture

- **Write permission depends on time.** Superadmin can always write. A dueño can write a month only if their depto is responsible for it (it holds the turno or receives a delegation of it). The window runs from day 1 of the month until `WRITE_GRACE_DAYS` (5) days after their unbroken responsibility ends: 501 can fix August during September, and both months until 5 October. Those days are the handover. In them, the outgoing owner closes their own months (`assertCanClose`) and records the next shift's handover (`assertCanHandOver` plus `ShiftScheduler.assertIsHandover`): the next depto takes it, or skips it and the outgoing depto or someone it picks covers. Only the superadmin reopens months. The next holder has no access to earlier months. Responsibility reaches the policy through the `ShiftResponsibility` port. This check is the domain `WriteAccessPolicy`, called from use cases, not only an HTTP guard. Whether the month is open is a separate check that `MonthlyCashbook` enforces.
- **The shift is computed, not stored per month.** The anchor is 2026-08 → depto 501, with fixed rotation 501→502→401→402→301→302→201→202→101→102 and 2 months per shift. The calendar never shifts for inactive deptos: an inactive depto's period has no responsible units until the superadmin assigns a cover with a `ShiftDelegation` (reason `INACTIVE_UNIT`, no penalty). A delegation stays within one scheduled period and overrides the months it covers. During it, both the original and the delegated depto can write while they are active. `ShiftScheduler` gets unit status through the `UnitAvailability` port, because domains never import other modules.
- **One monthly cashbook (`CashMovement`) holds every income and expense row:** `UNIT_PAYMENT`, `OTHER_INCOME`, `GARBAGE`, `CLEANING` and `OTHER_EXPENSE`. Its list view is the turn admin's main screen, and the monthly report is the opening balance plus that month's rows. Add, edit and remove go through one set of use cases, with a validation strategy per category.
- **Rows are cash-basis:** the row's date sets its month. Garbage is one $150 row per week, suggested as pending until it is confirmed. Cleaning is one row per visit. Weekly grouping is only a payout summary.
- **Garbage weeks:** a garbage row stores the Monday of the week it pays for (`week`, column `covers_week`), never derived from its date, so a week paid late or in another month still counts as paid. A week belongs to the month of its Saturday, the payday (`GARBAGE_PAYDAY`). Each week is paid once (`assertWeekUnpaid` through `CashbookAccess.assertConsistent`, plus an exclusion constraint). Pending weeks are computed by `garbageSchedule` and never stored or counted in totals; confirming one is a plain `POST /api/movements`.
- **Billing:** monthly `Charge`s (fee, plus a $500 skip penalty per skipped month, from `shiftSkipPenalties`; with the regular fee that makes the spec's $1,200 per month) are keyed by depto, month and type. `UNIT_PAYMENT` rows cover them oldest-first through `allocatePayments`, a pure function recomputed from scratch after any edit. Adeudo, adelanto and partial payments are derived in `AccountStatement` and never stored.
- **Editing:** rows can be edited or soft-deleted while the month is open, with audit, and allocations are recomputed. A closed month is frozen.
- **The monthly report** is opened from its first day by whoever can write the month, or by the daily job (earlier unopened months open first, and opening charges the month's fees), then closed once it is over and after the month before (which stores a snapshot) by the outgoing owner within their window or by the superadmin, and reopened only by the superadmin. A closed month also freezes its delegations and their penalties. Nothing is recorded before the superadmin sets the reporting start (first month and cash on hand). `ReportLedger` opens and closes months in order. An open month's balances are live, from the previous month's closing balance; a closed month answers with its snapshot. Re-closing a reopened month restates the later closed months, stopping at the first open one.
- **The audit log is append-only and enforced in the database** by a trigger plus revoked UPDATE/DELETE grants.
- **The rate settings** (`RateSettings` in the `settings` module: fee, cleaning rate, garbage amount, penalty) have effective dates. Changes are only appended after the latest one, so they never rewrite past months.

## Frontend conventions

- `@/*` resolves to `frontend/src/*`. Code is organized by feature under `src/features/<feature>/` (`api.ts` for Query hooks, `components/`, `routes/`).
- Routing and data use TanStack Router and TanStack Query. Screens other than login and home are declared with `lazyRouteComponent` in `app/router.tsx`, so each is its own chunk; in tests, wait for their content with `findBy…`. The route tree is declared in code in `app/router.tsx` (screens stay in `features/<feature>/routes/`), and guards live in `beforeLoad`. Forms use react-hook-form with the Zod schemas from `packages/shared`.
- **Session:** `lib/session.ts` keeps the user and the access token in memory only; the refresh token is an httpOnly cookie. Call the API through `getJson`/`sendJson` in `lib/http.ts`, which attach the token and refresh once on a 401. Components read the user with `useCurrentUser()`. Tests render the whole app with `renderApp(path)` and stub the API with `fakeApi()` (`src/test/`).
- **Theme and accents:** the theme follows the OS (`dark` variant = `prefers-color-scheme`, dark tokens in that media query in `src/index.css`); there is no toggle. Money in and out is marked with a border in `--income`/`--expense` (`border-r-income`, `border-b-expense`…), never by coloring text. «Atrás» lives in `AppLayout`; `app/back-navigation.ts` says where it leads when there is no earlier screen.
- PWA: `public/manifest.webmanifest` and `public/icons/` (generated from `favicon.svg` and `icons/icon-maskable.svg` with ImageMagick, 8-bit RGBA). `shadcn` is a dev dependency: only its CSS is used, at build time.
- shadcn style `base-lyra` is built on **Base UI (`@base-ui/react`), not Radix**, and uses **Phosphor icons**. Add components with `pnpm dlx shadcn add <component>` from `frontend/`. Tailwind v4 is configured through `@tailwindcss/vite`, with theme tokens in `src/index.css` and no `tailwind.config`.
